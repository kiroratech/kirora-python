# Contributing

Thanks for helping improve the Kirora Python SDK.

## Questions and support

For help with your integration, email **support@kirora.io**. Issues are for bugs and
feature requests only.

## Security issues

Don't open a public issue. See [SECURITY.md](SECURITY.md).

## Reporting bugs

[Open an issue](../../issues/new/choose) using the bug report form. A minimal code
sample that reproduces the problem is the most useful thing you can include.

## Pull requests

Small fixes (bugs, docs, typos) are welcome as pull requests directly. For new features
or changes to the public API, please open an issue first so we can agree on the
approach. Kirora's SDKs share the same API across platforms, so these changes need to be
designed together.

Before submitting:

- Add or update tests in `tests/`, in files named `*_test.py`. `tests/conftest.py` has a
  `Server` that answers requests through `httpx.MockTransport` and records what was
  sent; `server.install()` points the module settings at it, and `server.client()` makes
  a `Kirora` client for it.
- Run the checks below.
- Update the README, `docs/usage.md` and the examples if you changed public behaviour,
  and add a line to `CHANGELOG.md`.
- Don't edit `src/kirora/types.py`, `_error_codes.py`, `_webhook_events.py` or
  `_operations.py` by hand. They're generated by `scripts/codegen.py` from the API spec
  that `spec/source.json` pins, and CI fails if they're out of date. Maintainers move the
  pin when the API changes, so pull requests shouldn't change it.

## Development

```sh
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

pytest
mypy                       # the SDK, strictly
mypy --strict examples     # the examples, as a user's code
pyright
ruff check src tests scripts examples
ruff format --check src tests scripts examples
python scripts/codegen.py --check
```

### Updating the API spec

1. Set `url` in `spec/source.json` to the new commit's raw URL, and run
   `python scripts/codegen.py`. It fails with the `version` and `sha256` to set.
2. Set them, run it again, and review the diff of the generated files.
3. Run the checks, and update resource methods for any operation that changed.

To try a spec that isn't published, pass its path: `python scripts/codegen.py
path/to/openapi.json`. Nothing is checked against `spec/source.json` then, so don't
commit the result.

### Adding a method

The SDK follows the layout of [Resend's Python SDK](https://github.com/resend/resend-python):
each resource is a package, as `src/kirora/contacts/`, with the resource class in
`_contacts.py` and its models in `_contact.py`.

1. Add the operation's id to `OPERATIONS` in `scripts/codegen.py`, and regenerate, so its
   types exist. A list's query parameters become `{OperationId}Params`.
2. Add a class method to the resource class, and an `_async` one beside it with the same
   parameters: the ids in the path first, then `params` (the body, or a list's filters),
   then `options`. Name its request type on the class, as
   `IdentifyParams: TypeAlias = IdentifyContactInput`. Type `options` as
   `IdempotentCallOptions` if the operation takes an `Idempotency-Key`, and `CallOptions`
   if not. A contact id takes `id_type` as a keyword.
3. Add the call to `CALLS` in `tests/resources_test.py`, which checks that every wrapped
   operation has a method, and test it in the resource's `_test.py` and `_async_test.py`.
4. Add or update the resource's example in `examples/`.

## Releasing

Bump `__version__` in `src/kirora/version.py`, move the `CHANGELOG.md` entry under the
version and date, and merge. Then push a matching tag, such as `v0.2.0`: the release
workflow tests, builds and publishes it to PyPI through trusted publishing.
